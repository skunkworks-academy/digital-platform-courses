# Module 6: Deploy, observe, troubleshoot and govern cloud services

**Suggested time:** 45–70 minutes. **Competency:** The operational runbook correlates evidence to hypotheses and contains an authorised, tested rollback path.

## Concepts and architecture

A secure cloud rollout begins with requirements, environment separation (development/test/production), approvals, tracked configuration and repeatable deployment. Infrastructure as Code allows a reviewed definition of resources; it is not automatically secure. Monitoring includes availability, latency, error rate, resource utilisation, cost and security events. An incident response sequence identifies who is affected, which component is faulty, what changed and how to roll back safely. Logs and metrics answer different questions: metrics quantify performance, while logs show detailed events. Protect monitoring systems against storing credentials or sensitive payloads. Release checklists should include ownership, access review, recovery test, alert routing and documented rollback.

## Workplace scenario

A course site returns HTTP 503 for some users after a deployment. Identify the error budget and service health, inspect the app and dependency logs, test a rollback in staging, then communicate a bounded incident update.

## Applied exercise

1. Write a seven-step deployment checklist including scope, approvals, tests, secrets, monitoring, rollback and owner.
2. Define three service metrics and two alert thresholds for a fictional cloud web application.
3. List the diagnostic evidence required for an application failure versus a DNS problem.
4. Prepare a brief incident report with timestamp, scope, hypothesis, observation and remediation.
5. Propose one preventive policy guardrail and explain how it would be tested.

## Validation and reflection

The operational runbook correlates evidence to hypotheses and contains an authorised, tested rollback path. Create a verification register with **expected state**, **observed state**, **evidence**, **risk**, **owner** and **follow-up**. At least one test must demonstrate permitted activity and another must show an improper action is blocked or a faulty assumption is detected. Do not perform tests on systems without permission.

### Review questions

1. What distinguishes metrics from detailed logs?
2. Why should recovery and rollback be tested before release?
