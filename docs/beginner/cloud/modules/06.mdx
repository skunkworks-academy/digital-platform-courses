# Module 6: Cloud pricing, governance and a safe first deployment

**Time:** 50–70 minutes. **Learning criterion:** The plan has an authorised owner, capped assumptions, safe resource design and a scheduled removal procedure.

## Understand the concepts

Cloud bills may measure compute hours, provisioned capacity, stored gigabytes, requests, bandwidth, region and optional support. Free tiers can have eligibility and usage limits; a subscription without guardrails may incur charges. Build an estimate from documented quantities and current official rates before deploying. Apply resource tags, a named financial owner, budget alerts, quotas and an explicit teardown date. A production-ready pilot requires identity, logging, least-privilege networking, valid backups, test evidence, incident ownership and rollback.

## Workplace example

A fictional company wants a four-week pilot of an online brochure and enquiry form, using no real customer information and no more than an approved budget.

## Guided practical activity

1. Create a cost worksheet with quantity, unit, estimated price, total and uncertainty columns.
2. Compare a static hosted page, managed application and always-on virtual machine conceptually.
3. Set fictional budget thresholds and a cleanup date and list charges that might exceed expectations.
4. Write an approval/validation/teardown checklist and explain a potential exception.

## Confirm the learning

The plan has an authorised owner, capped assumptions, safe resource design and a scheduled removal procedure. In a table, record expected behaviour, observed or simulated behaviour, evidence, risk and next step. At least one negative test must show how an unsafe request is denied or escalated.

:::warning Safe use
Do not create live billable cloud resources or assume trial credits cover all usage without approval.
:::

## Extended learning: cost management and safe deployments

Cloud spend can arise from compute time, storage, databases, requests, network traffic and support plans. A low initial price does not mean the final bill is fixed. Budgets and alerts should be configured **before** starting chargeable experiments. Tags, ownership and regular reviews help teams identify idle services.

### Worked example: fictional monthly estimate

| Cost category | Illustrative estimate |
|---|---:|
| Small app runtime | 120 units |
| Storage | 30 units |
| Outbound data | 50 units |
| Database | 100 units |
| **Estimated total** | **300 units** |

These numbers are **illustrative only**, not a provider quotation. Verify actual current regional rates with the relevant pricing calculator. A 20% contingency on this example is 60 units, giving a planning allowance of 360 units.

### Controlled first deployment

1. Define the workload, expected users and business owner.
2. Choose the service model, region, access pattern and recovery requirement.
3. Estimate consumption and set budget alerts plus spending reviews.
4. Specify role-based permissions and prohibit shared admin credentials.
5. Test a fictional deployment and failed-access scenario before any real launch.
6. Define rollback, backup restore and criteria for decommissioning.
7. Shut down unneeded trial resources and confirm final billing state.

**Practice:** Explain why an orphaned test environment can continue generating charges. Write a release checklist with explicit ownership, cost controls, a sign-off gate and a safe decommission procedure.
