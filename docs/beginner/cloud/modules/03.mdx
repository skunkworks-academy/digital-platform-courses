# Module 3: Cloud architecture: regions, networks, compute and storage

**Suggested time:** 45–70 minutes. **Competency:** The diagram is coherent, segregates sensitive services and identifies realistic failure boundaries.

## Concepts and architecture

A region is a geographic market or area with provider infrastructure; availability zones are separate facilities within a region for fault isolation where a product supports them. Resources may be deployed in a virtual private network or VPC/VNet with subnets, routes and security controls. A virtual machine provides general-purpose compute; containers package applications, while serverless compute executes code without managing traditional servers. Object storage suits durable files and unstructured data, block storage supports virtual disks, and file shares support shared filesystem semantics. DNS maps names to destinations; content delivery networks place cached content nearer clients. Actual durability, replication and recovery depend on configured service tiers.

## Workplace scenario

A fictional online learning portal requires a public web entry point, protected student records and downloadable public course images. Separate public static content, application processing and nonpublic database storage.

## Applied exercise

1. Draw a labelled architecture with learner browser, domain/DNS, HTTPS endpoint, application layer, identity, database and object storage.
2. Mark which resource must be public and which must never allow anonymous direct access.
3. Place the deployment into a hypothetical region and identify a data-residency consideration.
4. Choose a compute model and two different storage models with a clear rationale.
5. Explain the potential consequences of a single availability-zone failure and a complete regional outage.

## Validation and reflection

The diagram is coherent, segregates sensitive services and identifies realistic failure boundaries. Create a verification register with **expected state**, **observed state**, **evidence**, **risk**, **owner** and **follow-up**. At least one test must demonstrate permitted activity and another must show an improper action is blocked or a faulty assumption is detected. Do not perform tests on systems without permission.
