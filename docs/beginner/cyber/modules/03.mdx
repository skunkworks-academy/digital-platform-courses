# Module 3: Passwords, passkeys and multifactor authentication

**Learning time:** 45–60 minutes. **Outcome:** understand and apply this protective capability in an authorised home or small-business setting.

## Understand the threat and control

Use unique long passwords or passkeys and a reputable password manager. Multi-factor authentication (MFA) combines independent factors such as a secret and a device or biometric unlock. Phishing-resistant methods such as FIDO2 security keys/passkeys improve resistance to impersonation. SMS codes may still protect better than password-only access but are vulnerable to some attacks. Backup methods and recovery codes need secure handling. Never share one-time codes or approve unexpected push requests.

## Practical case

A colleague repeatedly receives login approval prompts they did not initiate. They deny the prompts, report the incident and change credentials from a trusted session if indicated.

## Guided exercise

1. Draw an access plan for three fictional roles: owner, cashier and contractor; give each unique identity, MFA and least required permissions.
2. Create a simple table with **risk, evidence, control, owner and review date**.
3. Model a successful authorised action and an unauthorised or failed action; explain how the control responds.
4. Record observations, assumptions and recommended next steps separately.

## Avoid these mistakes

Test the recovery plan in a non-production account and record where recovery codes are securely stored without copying them into the report.

## Knowledge checkpoint

1. Explain the primary control and the harm it reduces.
2. What evidence would prove the control worked, and what would trigger escalation?

## Extended learning: build reliable authentication and account recovery

A **password** is something you know, a **security key or authenticator** is something you have, and a biometric can be used to unlock an approved device or authenticator. MFA combines independent factors. Passkeys based on modern FIDO standards bind authentication to the legitimate site, making them resistant to many credential phishing attacks. SMS one-time codes still provide some protection over a password alone, but are not phishing-resistant.

### Worked example: protect three fictional staff roles

| Role | Access requirement | Authentication and recovery |
|---|---|---|
| Cashier | Sales application only | Individual account, MFA and supervised recovery |
| Manager | Reports and approvals | Individual stronger authentication, reviewed permissions |
| Contractor | Time-limited support access | Expiring access, scoped permissions and recorded removal |

1. Give each role its own identity; do not distribute a shared password.
2. Record the minimum application actions required for the role.
3. Select MFA suitable for the service and user; prefer passkeys/security keys where available.
4. Design an offboarding step that disables access and revokes active sessions.
5. Write a recovery procedure that prevents a help-desk impersonator from taking over an account.

### Recognise the failure mode

Repeated sign-in prompts that the user did not request may indicate an attacker has a password. The correct response is **deny the prompt, report it and follow the organisation's recovery process**. Never approve a push notification just to make it stop. Recovery codes are secrets: document their storage location, not their values, in a course portfolio.

**Practice:** Simulate an account recovery phone call. Identify two identity-verification steps that do not ask a user to reveal a password or live one-time code.
