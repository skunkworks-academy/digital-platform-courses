# Module 5: Teams, OneDrive and collaborative work

**Study time:** 50–70 minutes. **Outcome:** apply this productivity capability using accurate, accessible and appropriately shared information.

## Learn the principles

Teams channels bring conversations and shared files together. Files often live in a connected SharePoint site; OneDrive is commonly for individual work files and controlled sharing. Choose owners, members and guests deliberately, and review external sharing before inviting collaborators. Comments, mentions and version history support review, but not every user should be able to approve final content. Record decisions and meeting follow-up actions.

## Worked business case

A four-person team is collaborating on a client proposal; one external reviewer needs access to only a single approved draft. Choose a limited share, define owner and an end date, and verify the reviewer cannot browse unrelated files.

## Practical walkthrough

1. Create a fictional project folder map and role matrix; prepare a safe link for an approved reviewer; document how you would revoke access and examine version history.
2. Capture the task objective, input data or document version, expected result and who will review it.
3. Produce a draft artefact or spreadsheet formula, then check one ordinary and one erroneous/unauthorised condition.
4. Correct the observed issue and preserve a simple change history.
5. Produce a short user-facing explanation of the final result and any outstanding limitation.

## Errors to avoid

Never assume access to a Teams channel automatically means permission to every confidential file used by the project.

## Knowledge and reflection checkpoint

- Which two checks must be performed before a document or calculation is shared?
- How would a colleague reproduce your work and detect a missing or incorrect value?

## Extended learning: collaborative access, versioning and ownership

OneDrive typically supports personal working files while SharePoint team libraries offer a team-managed location. Teams makes shared conversations easier but is not a substitute for checking file permissions. A pasted sharing link may provide more access than intended.

### Worked example: review a draft policy

1. Place a fictional policy document in a permitted team workspace.
2. Assign the document owner and a reviewer responsible for sign-off.
3. Give the reviewer edit access, while recipients who only read the final document receive view access.
4. Collect comments and use version history to record changes.
5. Remove temporary access when the review ends.
6. Test with a permitted account that an unauthorised reader cannot open the link.

| Symptom | Investigate |
|---|---|
| Access denied | Identity, tenant, permissions and link scope |
| Conflicting changes | Co-authoring state and version history |
| Wrong document shared | File name, version, owner and location |
| Anonymous editor can open | Link settings and excessive privileges |

**Practice:** Design an access matrix covering owner, editor, guest reviewer and learner. Label exactly which role can view, edit and reshare. Do not use real student documents to demonstrate mistakes.

### Sharing permission review: a worked negative test

Suppose a guest reviewer only needs a view-only copy of a draft guide. A learner should verify the link's audience, permitted operations and expiry before sharing. Record **expected: invited reviewer can read** and **expected: unrelated account is denied**. Where a real guest account is unavailable, describe a tabletop simulation rather than claiming you tested a live tenant. A strong evidence note includes the file owner, intended reviewers, permissions, observed or simulated result, correction and residual risk.

Avoid uploading real learner lists to demonstrate permissions. If a link turns out to be publicly editable, stop distribution, have an authorised owner replace or revoke the link, and document the change.
