# Module 2: Support tickets and diagnostic reasoning

**Estimated time:** 45–70 minutes. **Outcome:** Every ticket includes impact, symptoms, attempted steps, timestamps and verifiable acceptance criteria.

## Core concepts and why they matter

An incident is an unplanned service interruption; a service request is a routine fulfilment need. Capture the user's symptoms, actual impact, start time, recent changes, error messages, reproducibility and affected users. Use an evidence-first cycle: observe, form hypothesis, select low-risk test, evaluate, fix, verify and document. Priority considers business impact and urgency; the loudest user is not automatically the highest priority. Ask permission before remote access and avoid collecting unrelated personal information.

## Worked workplace scenario

Ten people cannot sign in to a web service while one user also needs a mouse replaced. Explain incident priority and what shared dependency you would test first.

## Guided hands-on application

1. Create tickets for a password reset, failed Wi-Fi connection and a printer queue backlog.
2. Choose category, impact, urgency, ownership and an agreed response time for each.
3. Write two alternative root-cause hypotheses for a single issue.
4. Create a closure checklist requiring user confirmation and observed functionality.

## Verification and failure test

Every ticket includes impact, symptoms, attempted steps, timestamps and verifiable acceptance criteria. Create a table identifying expected result, actual result, date, supporting evidence and next action. Use one deliberately invalid or unexpected input to confirm the control does not silently fail.

:::warning Safety and ethics
Do not request users' passwords or one-time codes to troubleshoot sign-in failures.
:::

## Evidence checklist

- [ ] Written purpose and accepted input.
- [ ] Reproducible procedure and observed result.
- [ ] Negative or failure test, with safe remediation.
- [ ] Reflection and next improvement.

## Extended learning: build repeatable diagnostic tickets

An incident ticket records a service interruption; a service request is a planned change or access request. A useful ticket separates **symptoms**, **impact**, **recent changes**, **tests**, **results** and **next owner**. Avoid premature root-cause claims such as “network broken” when the only observation is that one website did not load.

### Worked example: login failure

A fictional user cannot sign in to a training portal. Collect:

| Field | Example entry |
|---|---|
| Reported at | 09:10, local time |
| Affected scope | One user; three others unaffected |
| Exact symptom | “Account requires additional verification” |
| Known change | User changed mobile device yesterday |
| Approved test | Confirm account status and approved recovery process |
| Escalation | Identity administrator if MFA method cannot be recovered |

1. Ask for the exact error text but **not** the password or one-time code.
2. Reproduce a harmless part of the issue with the user.
3. Compare affected and known-good conditions, changing only one factor at a time.
4. Record the expected result, actual result and time of every test.
5. Escalate when administrative access, potential compromise or data loss is involved.

### Severity and communication

Impact asks how many people or services are affected; urgency asks how quickly the consequence matters. A single payroll failure may be more urgent than a cosmetic issue affecting many users. Explain the triage rationale in plain language.

**Practice:** Write a five-line ticket for “The printer doesn't work”. Replace vague language with device name, affected users, observations and specific reproducible steps.
