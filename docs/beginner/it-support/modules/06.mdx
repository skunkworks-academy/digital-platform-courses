# Module 6: Customer communication, escalation and evidence-based closure

**Estimated time:** 45–70 minutes. **Outcome:** The hand-off allows a second technician to continue without re-asking already answered questions.

## Core concepts and why they matter

Good support includes listening, confirmation, plain language, realistic estimates and a clear next update. The service desk must protect privacy, follow change control and give users an unambiguous workaround when the final fix is pending. Escalate based on technical boundary, security risk or service-level commitments. Capture actions in an objective chronological ticket without passwords. Knowledge-base articles should state symptoms, applicable versions, prerequisites, low-risk tests, corrective procedure and validation.

## Worked workplace scenario

A remote employee needs to join a call, but audio fails. The agent provides a tested temporary dial-in option, documents scope and escalates the driver issue.

## Guided hands-on application

1. Write a user-friendly acknowledgement for a high-impact connectivity ticket.
2. Prepare a 100-word escalation hand-off with evidence, attempts, business impact and next action.
3. Create a knowledge-base article for a recurring print queue issue.
4. Draft a closure message explaining the cause, what was changed and how the user can verify it.

## Verification and failure test

The hand-off allows a second technician to continue without re-asking already answered questions. Create a table identifying expected result, actual result, date, supporting evidence and next action. Use one deliberately invalid or unexpected input to confirm the control does not silently fail.

:::warning Safety and ethics
Do not promise a restoration time without evidence or claim a permanent fix when only a workaround was tested.
:::

## Evidence checklist

- [ ] Written purpose and accepted input.
- [ ] Reproducible procedure and observed result.
- [ ] Negative or failure test, with safe remediation.
- [ ] Reflection and next improvement.

## Extended learning: support quality includes user confirmation

Technical resolution is not the same as a useful service outcome. A support hand-off must let another technician continue without repeating all earlier questions. A closure note should identify the root cause **only when supported**, corrective action, verification evidence, user confirmation and outstanding risk.

### Worked example: a resolved sign-in ticket

A fictional trainee reports that the portal cannot be accessed after a new phone setup.

1. Listen and restate the symptom using non-judgemental, plain language.
2. Explain which safe checks you will perform and which permissions are needed.
3. Document the verified account status, error and approved recovery action.
4. Ask the learner to repeat the original sign-in task.
5. Close only after the learner confirms the expected result or explicitly accepts a documented workaround.
6. Record the article, runbook or escalation detail that would shorten the next incident.

### Compare weak and useful hand-offs

| Weak closure | Evidence-led closure |
|---|---|
| “Fixed” | “Learner signed in successfully at 11:22 after approved method reset” |
| “Network issue” | “DNS lookup failed for approved test name; other sites reachable” |
| “User mistake” | “New phone required account recovery; guidance updated” |

**Practice:** Write a customer-facing update limited to 80 words. Include the impact, what was checked, result and next action. Avoid exposing internal logs, blaming the user or promising an unsupported deadline.

**Reflection:** What would prove that the solution remains stable tomorrow? Identify an appropriate follow-up or monitoring action.
