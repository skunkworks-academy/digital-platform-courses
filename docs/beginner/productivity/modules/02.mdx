# Module 2: Professional documents and email communication

**Estimated study:** 45–70 minutes. **Capability outcome:** The artefacts communicate verified information, clear next actions and accessible structure without disclosing restricted content.

## Explanation and concepts

Readable work documents have a defined audience, a descriptive title, built-in heading styles, consistent terminology and an actionable conclusion. Built-in heading structures improve navigation and accessibility; manual bold formatting does not always create semantic headings. In email, a useful subject signals the request, the opening provides context and the final sentence states the action or deadline. CC is visible to recipients; BCC hides recipients from each other but should not be used to conceal improper disclosure. Attachments and shared links have different access and expiry implications. Calendar invitations should include date, time zone, location, agenda and preparation materials. Verify recipients and file sensitivity before sending.

## Worked business situation

A supplier asks about an invoice but the team has not approved a payment date. Draft a professional response acknowledging the enquiry without inventing terms or disclosing the organisation's internal finance records.

## Follow-along practical

1. Create a one-page fictional internal update with a title, level-two headings, a short table and a clear next action.
2. Draft two variations of an email: a formal external response and a concise internal request, both with meaningful subjects.
3. Inspect an attachment versus a shared-link approach and record which permissions are required in each case.
4. Create a meeting agenda with purpose, three time-boxed items, owner, time zone and expected decision.
5. Review the documents for spelling, heading structure, accessible links and prohibited disclosure.

## Validate and improve

The artefacts communicate verified information, clear next actions and accessible structure without disclosing restricted content. Build an evidence table with **expected result**, **observed result**, **data source**, **decision**, **next action**. Include one valid and one deliberately invalid input. If a simulated environment is used, label the simulation clearly.
